# Check: sub-11-12 — Cache the hunt (an instant read instead of a multi-minute re-search)

**Date:** 2026-08-06
**Branch:** main
**Verdict:** PASS (the redesigned hunt page is meant to be legible to anyone who opens it — but it
was not *openable*. `GET /api/monotransit/hunt` re-ran the whole single-transit pipeline on every
cached star on every request, a multi-minute spinner with no feedback. This sub-phase memoizes the
search on disk, keyed to the light curve's mtime, so a warm pool is an instant read. It is a pure
performance change: the cached answer is byte-identical to the recomputed one — the memo never
touches what the tool *says*, only how long it takes to say it.)

---

## Scope

`run_monotransit` is the expensive unit — light-curve load, detrend, sliding matched-filter search,
red-noise significance, and four discriminators. On a real TESS curve that is **minutes** of CPU.
The hunt runs it across the whole frontier pool, and re-ran it from scratch on every request. That
is the obstacle to "approachable for everyone": a page a first-time visitor must wait minutes for,
with nothing on screen, is not approachable.

The search is **deterministic given the curve**: same curve in, same events out. So the result can
be memoized and only recomputed when the input actually changes. A per-star `mono_*.json` in the
existing cache dir stores the result; two keys decide whether it is still valid:

```
lc_mtime_ns   the source light curve's (bls_lc_*.json) modification time — a re-fetch rewrites it
version       _MONO_CACHE_VERSION — bumped whenever the detection pipeline changes
```

A hit needs both to match. On a miss (either key differs, the file is corrupt, or it is absent) the
search recomputes and re-stores. Writes are atomic (temp file + `replace`) so a killed process
leaves the old result or the new one, never a half-written file that happens to parse.

## The version tag is load-bearing

The one real risk of a derived cache is the trap the vet cache sprang once (sub-11-1): a stale file
that still *parses* passes the schema and lies — old numbers read as current. The `mtime_ns` key
guards against a changed **curve**; `_MONO_CACHE_VERSION` guards against a changed **pipeline**. Any
change to the detection path — the significance floor `_SIG_MIN_MONO`, `_N_MIN_TRANSITS`, the
detrend window, the discriminators, the trapezoid model — MUST bump the version, or warm stars
would silently serve results from the old code. The tag is documented in the source with that rule,
in the imperative: *when in doubt, bump it.*

## The speedup is real, and the answer does not move

Measured on this machine:

```
cold compute : > 120 s   — a real plausible dwarf's cached curve (TIC 365725318); exceeds our
                           120 s command timeout, observed twice. This IS the bug: the old hunt
                           paid this, per cached star, on every single request.
warm read    :  0.21 ms  — best of 20, a synthetic curve's stored result; a pure JSON parse, and
                           the read path is the same size for a real dwarf (a handful of events).
```

Minutes to sub-millisecond. The exact cold seconds are unmeasured *because* the cold path is what we
are eliminating — it does not finish inside the window we allow a command. The identity of the
answer is the safety property, and that is pinned exactly:
`test_cached_result_matches_the_uncached_search` asserts `run_monotransit_cached(name) ==
run_monotransit(name)`. The memo is a speed change and nothing else.

---

## Why it is honest

- **The tool still never pretends to have looked where it did not.** An unfetched star has no cached
  curve, so `run_monotransit_cached` falls through to `run_monotransit` and the honest
  `FileNotFoundError` still surfaces as `not_fetched`. The cache only ever remembers a *real* search.
- **A stale cache cannot outlive its input.** Re-fetch a curve and its mtime changes; the memo
  recomputes. Change the pipeline and the version bump recomputes. There is no path where a warm
  read serves a number the current code would not produce.
- **A broken cache degrades to correctness, not to a crash.** A corrupt or partial `mono_*.json` is
  ignored and recomputed, then healed. The worst case of the cache is simply the old behaviour —
  recomputing — never a wrong answer and never a failure.

## Honest boundary (carried forward)

This is plumbing, not discovery. It makes the page fast; it does not make a quiet star less quiet or
a rejected dip a planet. The instrument log still reads the same — four dwarfs searched, all quiet.
What changes is only that a visitor now *sees* that log the moment they open the page, instead of
staring at a spinner long enough to leave. The honest picture the hunt reports is unchanged; the
memo just delivers it in time to be read.
