## The tally that reads the caches, not my arithmetic

`scripts/tally_hunt.py` recomputes "N of 50 searched: quiet / insignificant / rejected / candidates"
from the on-disk caches. It is a pure reader:

- **searched** — a valid `mono_*.json` result on disk (version + light-curve mtime match); its
  top-event disposition is read via the same `_event_disposition` the hunt uses.
- **fetched, not searched** — the raw MAST curve (`lc_<slug>_<mission>.json`) exists but no valid
  mono result yet.
- **not fetched** — no curve on disk. Never faked, never counted as searched.

It never fetches and never recomputes, so a disagreement between its output and the instrument log
means the *log* is stale, not the sky. On first run it caught exactly such a drift: the numbered
batches in the log summed to 38, but three dwarfs (TIC 156004112, 231631019, 352402781) had been
fetched and searched earlier during sub-11-12/13 tooling and never added to the running total. The
real count was 41. The log now carries the tally-verified number.

This is the counterpart to sub-11-15. There, a hand *reading* of an event's disposition drifted (a
sub-threshold edge blip written up as a near-miss); here, a hand *count* of the events drifted. Both
fixes have the same shape: stop letting a human hand stand between the caches and the record.

## Why it stays honest

- **The tool surfaces computed facts, it invents none.** Dispositions come from the same cached
  search results the API serves; the count is a sum over them. Nothing is re-derived or estimated.
- **The pending/not-fetched distinction is preserved and honest.** A fetched-but-unsearched curve is
  reported as such, not as a search with no result.
- **The empty hands are not softened.** Fifty dwarfs, zero candidates. The sweep does not make a
  find more likely; it establishes, at full pool scale and Earth-to-Neptune sensitivity, what the
  quiet sky and a working edge gate produce: nothing loud that is also real.
