## Scope

The hunt (`GET /api/monotransit/hunt`) searches a star only if its light curve is on disk; the
rest are reported `not_fetched`. sub-11-5 measured that only 16 of the 50 frontier-pool stars are
small enough that a detectable single transit could be a planet — but a cache scan at open showed
the five cached TESS curves are all `too_big` or noise cases, and **zero** of the 16 plausible
dwarfs had ever been fetched. So the hunt, however honestly it ranks, was searching stars where a
detection could only be a star, and had never once looked at a star where it could be a world.

sub-11-7 closes that gap without dishonesty. Fetching is a slow, fallible MAST download, so it
must never sit in a request path pretending to be instant. The sub-phase splits the bridge:

- **issue** (`f9eaea6`): `docs/issues/issue-11-7-body.md`, the plan and success criteria (#55).
- **L1 — the plan** (`9f0b864`): `fetch_plan.fetch_plan(is_cached=None, stars=None)` reads the
  sub-11-5 triage, keeps the `plausible` stars, tags each `cached`/`pending` via an injectable
  cache check, and leans on `assess_pool`'s ordering to lead with the best target. Pure geometry
  plus a cache check — no network. Summary: `{plausible, cached, pending, best_target, best_min_planet_rjup}`.
- **L2 — the runner** (`03b11e5`): `fetch_targets(plan, fetch_fn=None, limit=4)` walks the
  pending targets and pulls each, bounded by `limit`, with `fetch_fn` injectable (default
  `hunt.fetch_lc_by_tic`). Every star gets an outcome — `fetched`, `already_cached`, `failed`
  (with reason), or `deferred` (budget spent). A thin local CLI, `scripts/fetch_plausible.py`,
  wires it to the real fetch to run offline.
- **L3 — the endpoint** (`51380ab`): `GET /api/monotransit/fetch-plan` returns the plan as a
  typed `FetchPlan`, declared before `/monotransit/{planet_name}` so the path is not swallowed.
  No network, no fetch.
- **L4 — the surface** (`feef4da`): the hunt page names the targets — how many plausible, how many
  searchable, how many waiting — the best target and its minimum planet radius, and states plainly
  that pending stars need a local fetch. `fetchPlanHeadline` / `fetchPlanBestTarget` /
  `fetchPlanPendingNote` are pure and tested.

## The real plan at open

`python ../scripts/fetch_plausible.py --plan` (no network) reports:

```
plausible targets: 16  cached: 0  pending: 16
best target: TIC 156004112  (>= 0.60 R_jup)
```

All 16 plausible dwarfs are pending — the honest starting state. The best target, TIC 156004112
(R_star 0.96), would at the detection floor reveal a companion no smaller than 0.60 R_jup — a
Neptune-to-Saturn-sized world, not an Earth, but a *planet*, not a star. The list is ordered by
that minimum radius, so a bounded fetch spends its budget on the smallest worlds first.

## Why the split is honest

The dishonest shortcut would have been a single `POST /fetch-and-hunt` that quietly downloaded
sixteen multi-megabyte curves inside one HTTP request and reported "done." That hides the cost,
the latency, and the failures, and invites a deployed instance to hammer MAST. Instead:

- **The plan is deterministic and network-free.** It is catalog geometry (`assess_pool`) plus a
  cache check. It can be surfaced, tested, and reasoned about with zero downloads — the request
  path never blocks on a network the tool does not control.
- **The fetch is explicit, bounded, and injectable.** `limit` caps the network calls; the fetch
  function is a parameter, so the orchestration is fully tested with a fake and the real download
  lives in a local script, not a web request. Every star's fate is recorded, including failure.
- **Report, do not pretend.** A target says `cached` or `pending`; a fetch says `fetched`,
  `already_cached`, `failed` (with the reason), or `deferred`. Nothing is ever claimed fetched
  that was not — the same honesty the hunt's `not_fetched` disposition already keeps.

The one deliberate design tension: `best-target-first` spends the budget on the smallest planets,
which are also the shallowest, hardest transits to recover. That is intentional — the point of
the whole path is the small worlds the machines miss; sorting toward the easy giants would defeat
sub-11-5's entire finding.

## Honest boundary (carried forward)

The plan rests on the sub-11-5 fiducial floor (0.40%) and the catalog stellar radius, so a wrong
radius still moves a star across the plausible/too_big boundary. And the plan proves only that we
*know which stars to fetch and in what order* — not that any of them holds a transit. The 16 are
pending; until their light is actually on disk, the hunt still searches nothing worth searching.
What sub-11-7 removes is the last excuse between the aim and the sky: the targets are named, the
fetch is a real, bounded, honest command away, and the moment one plausible dwarf's curve lands,
`GET /api/monotransit/hunt` will search a star where a detection could — for the first time in
this project — be a planet.

The true north-star step is now a single local run: `python ../scripts/fetch_plausible.py`, then
watch the hunt search a plausible dwarf. That run is network-bound and its result depends on what
TESS actually recorded, so it is its own step — but every deterministic thing that could be built
before it now is.

## Result

The instrument is no longer pointed at empty air. The 16 stars where a single-transit detection
could be a planet are named, ordered smallest-world-first, and one bounded command from having

gap between "we know where to look" and "we have looked" is now a script, not a missing design.
