## Why an older sector, and why a separate file

Sectors 104 and 105 are swept in full — 200 smallest-first dwarfs, zero candidates (sub-11-19/20).
The honest next real sky is either a *newer* sector (106 has not gone live — a MAST probe found it
empty, and TESS releases one roughly every 27 days) or an *older* one already on MAST but never hunted
for monotransits. A repeated-transit pipeline (BLS) filed the TOIs; the single transit it is blind to
is still unspent in every sector, old or new. So we turn to sector 103, the sector just before 104.

Hunting it could not just reuse the frontier pool file: the biweekly refresh Action rolls
`frontier_seeds_tess.json` to the *newest* sector, so overwriting it with 103 would fight that Action
and bury the current sector-105 record. Instead, the hunt scripts gained a `--pool PATH` flag (default
unchanged), and sector 103 was built to its own file:

```
build_frontier_seeds_tess.py --sectors 103 --n 100 --select hunt --out data/pool_s0103.json
  → sector 103: 13,000 SPOC targets, 12,663 absent from the TOI catalog
  → 100 smallest-first dwarfs, radius 0.160–1.066 R☉ (median 0.809), the smallest an R★ 0.160 M dwarf
```

The tracked frontier (sector 105, 100/100) is never touched; every hunt command here carries
`--pool data/pool_s0103.json`. Four of the 100 already carry a cached result (their TIC was hunted in
an earlier sector — the same star, the same curve, honestly counted), so the sweep begins at 4/100.
